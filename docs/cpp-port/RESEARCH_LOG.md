## Шаг 4. Вопрос библиотек
- **STL** (`<iostream>`, `<vector>`, `<string>`, `<algorithm>`, `<map>`…): на пути A — из коробки (libc++ в sysroot). Это паритет с Python-версией (там тоже только встроенная stdlib, не весь PyPI).
- **Header-only сторонние либы:** реализуемо через in-memory FS (потенциальный фичер «подключи свой .h»).
- **Либы с раздельной компиляцией/линковкой** (Boost-сборки, SDL): трудно, и для учёбы не нужны.
- **Чего не будет (нормально):** сеть, потоки, реальная ФС — песочница WASI/браузера (аналог CSP-блокировки в Python-версии).

## Шаг 6. wasi-sdk как production-база (закрытие `__lttf2` и C++20)
- **wasi-sdk** (https://github.com/WebAssembly/wasi-sdk) включает: `compiler-rt`, `libclang_rt.builtins-wasm32.a`
  (та самая недостающая библиотека → **чинит `__lttf2`**), `libc++.a`, `libc++abi.a`, полный sysroot.
- Современные релизы — clang 18+ → **C++20/23** из коробки (против C++14 у binji).
- **C++ исключения (try/catch):** в WASI **выключены по умолчанию**, включаются флагом сборки
  (`-DWASI_SDK_EXCEPTIONS=ON` при сборке sysroot + `-fwasm-exceptions` при компиляции).
  Опираемся на **нативный Wasm Exception Handling** (поддержан современными браузерами) — меньше размер и оверхед,
  чем старый JS-emulated. ⚠️ Для учебной C++-IDE исключения обязательны → закладываем сборку sysroot с EH.
- **Вывод:** базой берём самосборный/готовый тулчейн wasi-sdk, а не binji-demo. Архитектуру запуска — из binji.

## Шаг 7. stdin / console — ключевое архитектурное решение
**Проблема:** WASI `fd_read` синхронный; web-worker не может «заснуть» в ожидании `postMessage`,
не отдав event loop. Отсюда три модели ввода:

| Модель | Как работает | COOP/COEP? | UX |
|---|---|---|---|
| **Batch stdin** (рекоменд.) | весь ввод задаётся заранее как `Uint8Array`, программа читает `cin >>`/`fgets` | **не нужны** | поле «Ввод» + «Запуск» |
| Interactive (SAB) | worker блокируется на `Atomics.wait`, main пишет ввод в `SharedArrayBuffer` | **нужны** (cross-origin isolation) | живой `input()`-стиль |
| Interactive (JSPI/Asyncify) | async `fd_read` через JS Promise Integration или Asyncify-трансформ | не нужны (JSPI), но новее | живой ввод |

**Решение для МШ-контекста (Информатикс = олимпиадные задачи):** **batch stdin — основная модель.**
Студент пишет ввод в отдельное поле, программа читает его через `std::cin`. Это:
- точно ложится на стиль задач (ввод дан → программа читает → вывод);
- **не требует COOP/COEP** → работает на GitHub Pages (как и оригинал);
- тривиально реализуется (предзаполненный буфер stdin в WASI-shim).

**Интерактивный ввод — опционально, вторым этапом:**
- GitHub Pages не отдаёт COOP/COEP-заголовки → `SharedArrayBuffer` напрямую недоступен.
  Обход: **coi-serviceworker** (SW, инжектящий COOP/COEP на клиенте) — у проекта уже есть service worker.
- Либо **JSPI** (JS Promise Integration, Chrome 137+, 2025) — async stdin без cross-origin isolation. ⚠️ проверить охват браузеров.
- Готовый кирпич: **bjorn3/browser_wasi_shim** — WASI-shim для браузера (можно взять за основу stdin/FS).

## Шаг 9. emception vs wasm-clang (по данным Стэнфорда 2025)
- **binji/wasm-clang:** тот же core-компилятор без лишних обвязок → **быстрее компиляция (1.5–9.75×)**; легче; но старый.
- **emception:** прогоняет Binaryen-оптимизацию → **лучше оптимизирует код (-O2 на 1.2–3.4×)**, но тяжелее и медленнее компилирует;
  полноценный Emscripten (ports: zlib/SDL и пр.).
- **Выбор:** для учебной IDE приоритет — скорость отклика и простота, а не максимум оптимизации рантайма
  → **архитектура wasm-clang + современный sysroot wasi-sdk**. emception держим в уме, если понадобится Emscripten-экосистема.

## Шаг 10. Уточнение: «современный clang в браузере» — два пути к базе
Важное различие, всплывшее при разборе:
- **wasi-sdk** поставляет clang как **нативные бинарники** (для сборки на машине). Чтобы запускать clang *в браузере*,
  его сам надо скомпилировать в WASM — это нетривиальная работа (ровно её сделал binji для старого clang 8).
- **emception** — это и есть **clang/llvm, уже скомпилированный в WASM** через Emscripten, с современным sysroot,
  Binaryen и (предположительно) рабочими исключениями/C++20. То есть «готовый современный clang-в-браузере».

**Следствие для выбора базы (два кандидата на спайк):**
1. **emception** — взять готовую современную сборку clang-в-WASM (быстрый путь к рабочему C++20 + exceptions),
   ценой большего веса и Binaryen-обвязки.
2. **Самосборка а-ля binji, но на свежем LLVM + sysroot wasi-sdk** — легче и быстрее на компиляции,
   но требует собственной сборки LLVM→WASM (трудозатратно).

Конкретные характеристики emception (версия clang, точный размер, COOP/COEP, stdin) в README **не задокументированы** —
закрывается только **hands-on спайком** (склонировать `jprendes/emception`, поднять demo, замерить).
То же касается самосборного варианта. → Это следующий практический шаг исследования.

## Шаг 13. API-спайк emception — контракт интеграции (риск закрыт) ✅
Разобрали API-поверхность по бандлу demo (инстанс emception в коде = `Xe`). Подтверждено, что наш план поддержан API:

```js
Xe.onstdout = cb;  Xe.onstderr = cb;          // прямой захват потоков (demo шлёт в xterm → мы в нашу консоль)
await Xe.fileSystem.writeFile(path, source);   // in-memory FS: исходники многофайлового проекта
await Xe.fileSystem.readFile(outputPath);      // чтение артефакта сборки
Xe.exec(cmd);                                  // запуск тулчейна (em++/clang/wasm-ld/wasm-opt)
```
Всё async, исполняется в worker (`--proxy-to-worker`). Сообщения «Loading Emception…» / «Emception is ready».

**Важное разделение потоков:**
- `Xe.onstdout/onstderr` = stdout/stderr **самого тулчейна** (диагностика компилятора) → в наш блок «Компиляция».
- stdout/stderr **программы пользователя** — это уже артефакт сборки. В demo он идёт через emscripten-HTML-оболочку
  (`-o main.html` + canvas), что нам НЕ нужно. Решение: компилировать в **модуль** (`-sMODULARIZE`/`-o main.mjs`,
  без HTML-shell и canvas) и инстанцировать самим с кастомными `Module.print` (stdout), `Module.printErr` (stderr),
  `Module.stdin` (**batch-ввод**). Это стандартная emscripten-интеграция.

**Вывод:** ключевое допущение плана («захват stdout напрямую + batch stdin, без canvas») — **подтверждено на уровне API**.
Полная headless-реализация требует рабочей сборки emception (npm `@jprendes/emception` через GitHub Packages, либо Docker-сборка) — это задача этапа F0.

## Сравнительная сводка кандидатов (итог)
| | binji/wasm-clang | emception | Самосборка (modern LLVM) |
|---|---|---|---|
| Эпоха тулчейна | 2019, clang 8 | 2022, emsdk 3.1.24 (~LLVM 15/16) | свежий (18+) |
| C++ стандарт | C++14 | C++17 / частично 20 | C++20/23 |
| Исключения | ❌ (sysroot неполн.) | ✅ (Emscripten) | ✅ (настроить) |
| Sysroot/STL | неполный (`__lttf2`) | полный | полный |
| GitHub Pages | ✅ (нет COOP/COEP) | ✅ (brotli+wasm-package) | зависит от сборки |
| Скорость компиляции | быстрее (легче) | медленнее (Binaryen) | зависит |
| Готовность «из коробки» | demo, сыро | **наиболее готов** | надо строить |
| Трудозатраты внедрения | средние | **низкие (MVP)** | высокие |

**Рекомендация по базе:**
- **MVP** — взять **emception** как есть (быстрый путь к рабочему C++17/20 + исключения + GitHub Pages),
  приняв тулчейн 2022 года.
- **Зрелая версия** — переиспользовать build-пайплайн emception (Docker, `llvm-box`, brotli/`wasm-package`),
  пересобрав на **современном LLVM 18+** для C++23.
- binji — только как лёгкий референс архитектуры запуска; как продукт не годится.
