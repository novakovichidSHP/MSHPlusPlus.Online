# План реализации MVP: МШПлюсПлюс.Онлайн (C++)

> Основано на `RESEARCH_LOG.md` и `ТЗ_переработка.md`. База рантайма — **emception** (подтверждено руками, Шаг 12).
> Статус: черновик плана. Дата: 2026-06-11.

## Жёсткие правила (действуют на весь проект)
- **R1 — не ломать UX оригинала.** Сохраняем потоки работы, хоткеи, расположение блоков, поведение
  проектов/консоли/шеринга/импорта. Пользователь, знакомый с Python-версией, не должен «переучиваться».
- **R2 — вёрстка только через макет.** Любое изменение структуры `index.html` или layout-CSS
  предваряется **предварительным макетом** и согласуется до написания кода. Без аппрува макета — вёрстку не трогаем.
- **R3 — два независимых трека.** Функциональная замена рантайма (Python→C++) и визуальный апгрейд («повзрослее»)
  ведутся раздельно, чтобы не смешивать технические и дизайнерские риски.

## Трек F — функциональный (замена рантайма). Без изменения вёрстки.
Цель: тот же UI, но внутри — C++ вместо Python. Любые правки, затрагивающие layout, выносятся в Трек V.

### F0. Спайк интеграции (headless, без UI) — ✅ ДОКАЗАНО (2026-06-11)
> Контракт подтверждён руками: компиляция C++/STL **в модуль** + прямой stdout + batch stdin, без canvas.
> Вывод `n=5 sorted: 1 3 5 8 9 sum=26`, ~18 мс. Рецепт: `F0_harness_reference.md`, лог Шаг 15.
> Ниже — что именно проверено / как воспроизвести.
- **Рабочая сборка emception — ДОБЫТА** (Шаг 14 лога): прибилженные артефакты из ветки `demo` репозитория
  (`C:\_Vibe_coding\_research\emc-demo`, проверено локально — компилирует+запускает). npm/Docker не нужны.
- Подключить emception-модуль (worker), скомпилировать строку C++ → модуль → запустить.
- **API-контракт (подтверждён, Шаг 13 лога):** `onstdout/onstderr` (диагностика тулчейна), `fileSystem.writeFile/readFile`, `exec(cmd)`.
- **Захват stdout/stderr программы напрямую:** компилировать в модуль (`-sMODULARIZE`, без HTML-shell/canvas),
  инстанцировать с `Module.print` / `Module.printErr`.
- **Batch stdin:** `Module.stdin` отдаёт заранее заданный буфер; прочитать `std::cin`.
- Проверить: таймаут компиляции, таймаут выполнения, перехват ошибок компилятора (текст + позиция).
- Критерий: многофайловый C++17/20 со STL и `try/catch` компилируется/запускается, stdin/stdout работают.

### F1. Слой движка выполнения `cpp-runtime`
- Изолированный модуль в `assets/` — занимает «место Skulpt» в архитектуре.
- API: `compile(files, flags)`, `run(stdin)`, `cancel()`, события вывода/ошибок.
- Лимиты (адаптировать из оригинала): таймаут выполнения, `MAX_OUTPUT_BYTES`, лимиты файлов/проекта; **+ таймаут компиляции**.
- Дефолтные флаги: `-O2 -std=c++20 -fexceptions` (язык C++20; библиотека — по факту тулчейна).
- Без сети/потоков/реальной ФС (песочница WASI/emscripten).

### F2. Интеграция в существующий app
- Заменить вызовы Skulpt на `cpp-runtime` в `assets/skulpt-app.js` (точки: запуск, нормализация, точка входа, остановка).
- Редактор: переключить CM6 на C++ (`@codemirror/lang-cpp`) вместо Python.
- **Turtle — отключить рантайм** (перестать грузить `TURTLE_SHIM`/canvas-слой). ⚠️ *Удаление turtle-панели/карточки
  меняет layout → это вёрстка → идёт через Трек V и макет.* На этом шаге — только отключение логики, без правки DOM.
- Переименование сущностей `.py`→`.cpp/.h` в UI-строках — где не layout, делаем; где влияет на структуру — в Трек V.

### F3. Хранение / шеринг / импорт-экспорт
- Адаптировать модель данных под `.cpp/.h/.hpp` (вместо `main.py` → `main.cpp`).
- Шеринг/snapshot (gzip+base64url, SHA-256/FNV-1a) — переиспользуем как есть.
- Импорт/экспорт: расширения `.cpp/.h/.hpp/.zip/.json`.
- IndexedDB-хранилища (`projects/drafts/recent/trash`) — структура та же.

### F4. Диагностика компилятора
- Парсинг вывода clang (`file:line:col: error/warning`) → кликабельные ссылки на строки в редакторе.
- Раздельные блоки: вывод программы (stdout) / ошибки компиляции / stderr программы.
- *Если потребуется новый блок/панель в UI — через макет (Трек V).*

### F5. Тесты
- Unit (Node test runner): утилиты `cpp-runtime`, парсер ошибок, модель файлов, импорт/шеринг.
- E2E (Playwright): компиляция → запуск → корректный вывод; ошибка компиляции; batch stdin; шеринг по ссылке; recent/trash.
- Адаптировать существующие e2e под C++-сценарии; turtle-тесты удалить.

## Порядок и зависимости
1. **F0** (спайк) — стартуем первым, он снимает главный технический риск.
2. Параллельно **V0/V1** (направление + макеты) — т.к. визуал и удаление turtle = вёрстка, нужен ранний аппрув.
3. **F1→F2→F3→F4** — после успешного F0; layout-затрагивающие части ждут аппрува макетов из V1.
4. **F5** — по мере готовности модулей.
5. **V2** — после аппрува макетов.

## Ключевые риски и митигивции
- **Вес тулчейна (десятки МБ) и UX первого запуска** → экран загрузки с прогрессом (макет V1), кеш (service worker), brotli.
- **C++20 библиотека (`<ranges>`) неполная в тулчейне 2022** → для MVP ок (язык C++20 + STL есть); свежесть — отдельной задачей (пересборка на LLVM 18+).
- **Интеграция worker/stdin** → отрабатывается в F0 до касания основного app.
- **Случайный слом UX/вёрстки** → защищено R1/R2 (макет-гейт) и e2e-тестами.
