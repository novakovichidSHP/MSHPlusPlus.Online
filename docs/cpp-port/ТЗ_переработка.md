# ТЗ: переработка МШПайтон.Онлайн → МШПлюсПлюс.Онлайн (C++)

> Статус: **черновик**, наполняется по ходу исследования. Основано на `RESEARCH_LOG.md`.
> Дата: 2026-06-11.

## 1. Цель
Переработать существующую браузерную Python-IDE (Skulpt) в **браузерную C++-IDE** для учебных задач,
сохранив архитектурные принципы оригинала:
- работа **без сервера и без аккаунтов**, всё выполняется в браузере;
- хранение проектов локально (IndexedDB);
- **шеринг по неизменяемой ссылке** (snapshot);
- импорт/экспорт проектов;
- размещение на статике (GitHub Pages-совместимо).

## 2. Ключевое изменение: рантайм
| Было (Python) | Стало (C++) |
|---|---|
| Skulpt (JS-интерпретатор Python) | **clang/LLVM → WASM в браузере** (настоящая компиляция) |
| Мгновенный старт, ~МБ | Холодная загрузка тулчейна (десятки МБ, кешируется) |
| `input()` интерактивный | **batch stdin** (поле ввода) как основная модель |
| turtle-графика | **удаляется** |

**Тулчейн (стратегия в две фазы):**
- **MVP — emception как есть** (`jprendes/emception`): clang/llvm уже скомпилирован в WASM, полный sysroot,
  рабочие исключения, C++17/частично C++20, и — важно — спроектирован под GitHub Pages (brotli + `wasm-package`).
  Тулчейн 2022 года (emsdk 3.1.24), но это самый быстрый путь к рабочему продукту.
- **Зрелая версия** — пересборка по build-пайплайну emception (Docker, `llvm-box`, brotli/`wasm-package`)
  на **современном LLVM 18+** ради C++23 и свежей STL.
- Дефолтные флаги компиляции: `-O2 -std=c++20 -fwasm-exceptions` (нативный Wasm EH).
- binji/wasm-clang — **только референс архитектуры запуска**, как продукт не годится (clang 8, неполный sysroot, баг `__lttf2`).

**Конвейер выполнения** (референс — binji/wasm-clang и emscripten-пайплайн emception):
1. исходники проекта → in-memory FS;
2. `clang -cc1 ... -o main.o -x c++ main.cc` (для каждого `.cc`/`.cpp`);
3. `wasm-ld ... crt1.o *.o -lc -lc++ -lc++abi -lclang_rt.builtins-wasm32 -o prog.wasm`;
4. запуск `prog.wasm` в Web Worker через WASI-shim;
5. stdout/stderr → консоль UI; stdin ← поле ввода (batch).

## 3. Что переиспользуется из оригинала (минимум изменений)
- Слой хранения: IndexedDB (`projects`, `drafts`, `recent`, `trash`) — структура почти та же
  (вместо `main.py` → `main.cpp`, модули `.py` → `.cpp/.h`).
- **Шеринг/snapshot** (gzip + base64url, `CompressionStream`/fflate, SHA-256/FNV-1a) — без изменений.
- **Импорт/экспорт** (.zip/.json; вместо `.py` → `.cpp/.h/.hpp`).
- **Роутинг** на хешах (`#/p/{id}`, `#/s/{shareId}`, `#/embed`) — без изменений.
- **Редактор CodeMirror 6** (`editor-core/`) — сменить языковой режим с Python на **C++** (`@codemirror/lang-cpp`).
- Общий UI-каркас: landing, topbar, панели, модальные окна, toasts, hotkeys.
- Тестовая инфраструктура: Playwright + unit (Node test runner).

## 4. Что удаляется / заменяется
- **Skulpt** (`assets/vendor/skulpt/`) → тулчейн wasm-clang/wasi-sdk (`assets/vendor/clang-toolchain/`).
- **Turtle**: `TURTLE_SHIM`, canvas-слой, turtle-карточка в mobile-nav, `turtle-runtime-utils` — убрать.
- **editor-legacy** — кандидат на удаление (в оригинале и так готовится к архивации); решить отдельно.
- Python-специфика в `skulpt-app.js`: нормализация исходника, `Sk.configure`, точка входа `__main__` →
  заменить на оркестрацию компиляции/линковки/запуска.
- Языковой режим редактора Python → C++.

## 5. Модель ввода/вывода
- **Вывод:** stdout + stderr раздельно (ошибки компилятора — отдельным блоком, с подсветкой).
- **Ввод (основной):** поле «Ввод (stdin)» → передаётся в программу целиком перед запуском (`Uint8Array`).
- **Ввод (опционально, этап 2):** интерактивный `cin` через coi-serviceworker+SAB или JSPI.
- **Диагностика компилятора:** показывать вывод clang (`-fcolor-diagnostics` маппить на HTML), номера строк кликабельны.

## 6. Лимиты и защита (адаптировать существующие)
- Таймаут выполнения программы (аналог `RUN_TIMEOUT_MS`).
- **Таймаут компиляции** (новый) + индикатор «компиляция…».
- Лимит размера вывода (`MAX_OUTPUT_BYTES`).
- Лимиты на файлы/проект (`MAX_FILES`, `MAX_SINGLE_FILE_BYTES`, `MAX_TOTAL_TEXT_BYTES`).
- Песочница: нет сети, нет реальной ФС, потоки ограничены (как WASI).

## 7. Производительность и загрузка
- Тулчейн (~десятки МБ) грузится один раз, кешируется service worker'ом; **прогресс-бар загрузки**.
- Стриминговая инстанциация WASM (`instantiateStreaming`), сжатие brotli на хостинге.
- Тёплый старт — из кеша; компиляция типовой задачи — цель «секунды, не десятки секунд».

## 8. Этапы реализации (предварительно)
1. **Спайк:** собрать/достать тулчейн wasi-sdk (clang+lld+sysroot) под WASM, проверить компиляцию+линковку
   STL и исключений (закрыть `__lttf2`, C++20, try/catch).
2. **Минимальный движок выполнения:** WASI-shim + worker + batch stdin + stdout/stderr → консоль.
3. **Интеграция в существующий UI:** заменить Skulpt-вызовы на движок; режим C++ в CM6; убрать turtle.
4. **Хранение/шеринг/импорт-экспорт:** адаптировать под `.cpp/.h` (минимальные правки).
5. **Диагностика компилятора:** парсинг/подсветка ошибок, клик по строке.
6. **Тесты:** unit (утилиты) + e2e (компиляция/запуск/ошибки/шеринг).
7. **Опционально:** интерактивный stdin; селектор `-std`/`-O`; «подключи свой `.h`».

## 9. Риски
- **Размер загрузки тулчейна** (десятки МБ) — главный UX-риск; митигируется кешем/сжатием/прогрессом.
- **C++ exceptions в WASI** — требуют корректной сборки sysroot; проверить в спайке.
- **Интерактивный ввод на GitHub Pages** — нет COOP/COEP; решается batch-моделью (основной путь) или coi-serviceworker/JSPI.
- Совместимость браузеров с Wasm EH и (опц.) JSPI/SAB — проверить матрицу.

## 10. Критерии приёмки (черновик)
- Компилируется и выполняется многофайловый C++17/20 проект со STL и `try/catch`.
- Корректный вывод stdout/stderr; ошибки компиляции читаемы и привязаны к строкам.
- Batch stdin работает; типовая задача «ввод → обработка → вывод» проходит.
- Шеринг по ссылке, импорт/экспорт, recent/trash — работают как в оригинале.
- Холодная загрузка с прогрессом; тёплый старт из кеша; turtle отсутствует, регрессий в UI нет.
- Размещается на статике (GitHub Pages) без серверных заголовков.
